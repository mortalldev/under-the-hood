## TL;DR

In an **event-driven architecture** services publish **events** — facts that already happened, like `OrderPlaced` — to a broker (Kafka, a cloud pub/sub, RabbitMQ). Other services **subscribe** and react on their own time. The publisher doesn't know who listens, so you can add consumers without touching it, and a slow or broken consumer doesn't slow down the publisher.

## How it works

- **Event, not command**: `OrderPlaced` (past tense, a fact) rather than `SendEmail` (an instruction to a specific service).
- **Topic / log**: Kafka stores events in an append-only, partitioned log. Each consumer group tracks its own **offset**, so it can lag, crash and resume, or even replay history.
- **Ordering**: guaranteed only within a partition. Use the entity id (`orderId`) as the key so all events for one order stay in order.
- **Delivery**: in practice **at-least-once** — a consumer can see the same event twice after a crash. Make consumers **idempotent** (dedupe by event id, or use upserts).
- **Publishing reliably**: write the event in the same database transaction as the state change (the **outbox** pattern), then relay it; otherwise a crash between "save" and "publish" loses the event.

## Code

```ts
// producer (kafkajs): key by order id → ordered per order
await producer.send({
  topic: "orders.placed",
  messages: [{ key: order.id, value: JSON.stringify({ id: crypto.randomUUID(), type: "OrderPlaced", orderId: order.id, total: order.total }) }],
});

// consumer: idempotent
await consumer.subscribe({ topic: "orders.placed" });
await consumer.run({
  eachMessage: async ({ message }) => {
    const event = JSON.parse(message.value!.toString());
    if (await processed.has(event.id)) return;      // duplicate → skip
    await sendConfirmationEmail(event.orderId);
    await processed.add(event.id);
  },
});
```

## When to use it — and when not

**Use it** when one action triggers many independent reactions (email, analytics, search indexing, fraud checks), when consumers must be decoupled from the producer's availability, and to feed read models, data pipelines or audit logs.

**Avoid it** when the caller needs the answer *now* (checking a password, reading a price): that's a request/response call. And don't model a workflow purely as events nobody owns — long chains of "A emits, B reacts, C reacts" become hard to follow; use an orchestrated saga for multi-step business processes.

## Trade-offs

| Gain | Cost |
| --- | --- |
| Producers and consumers evolve independently | Eventual consistency: consumers are behind |
| Absorbs spikes; consumers scale separately | Duplicates and reordering must be handled |
| Replayable history for new consumers | Debugging needs trace ids across async hops |
| | Event schemas become a long-lived contract |

Kafka was created at LinkedIn to move activity data between systems at this kind of scale.

## In interviews

<QA q="How do you make sure an event is published exactly when the database write commits?" level="senior">

Use the transactional outbox: in the same transaction as the state change, insert the event into an outbox table. A separate relay (or change data capture on the database log) publishes outbox rows to the broker and marks them sent. That gives at-least-once publishing without a distributed transaction, so consumers still need to be idempotent.

</QA>

<QA q="Kafka gives you at-least-once delivery. What does that mean for your consumer?" level="mid">

It may process the same event more than once, for example after crashing before committing its offset. The handler must be idempotent: record processed event ids, use upserts keyed by entity id, or check state before acting.

</QA>
