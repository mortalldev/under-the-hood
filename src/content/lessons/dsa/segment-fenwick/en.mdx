## TL;DR

When an array changes **and** you need range aggregates, prefix sums (O(n) update) and recomputation (O(n) query) both fail. A <Term id="fenwick-tree" /> gives O(log n) point updates and prefix sums in ~10 lines; a **segment tree** gives O(log n) for any associative aggregate (sum, min, max, gcd), and with lazy propagation also handles **range updates**.

## Visual model

```text
Fenwick: tree[i] covers (i − lowbit(i), i]     lowbit(i) = i & −i (lowest set bit)
i (binary)  covers
 1  0001    [1, 1]
 2  0010    [1, 2]
 3  0011    [3, 3]
 4  0100    [1, 4]
 6  0110    [5, 6]
 8  1000    [1, 8]

prefix(7) = tree[7] + tree[6] + tree[4]    (7 → 6 → 4 → 0: strip the lowest bit each time)
```

## Mechanism

- **Query** `prefix(i)`: add `tree[i]`, then jump to `i − lowbit(i)` — the end of the block before it. The number of jumps equals the number of 1-bits in i: ≤ log₂ n.
- **Update** `add(i, Δ)`: every block that contains position i must change. Those are `i, i + lowbit(i), …` — climbing to the next block that covers i. Also ≤ log₂ n.

A **segment tree** stores the aggregate of `[l, r]` at a node and splits it into `[l, mid]` and `[mid + 1, r]`. Any query range decomposes into O(log n) fully-covered nodes; an update changes the O(log n) nodes on one root-to-leaf path.

## Code

```ts
class Fenwick {
  private t: number[];
  constructor(n: number) { this.t = new Array(n + 1).fill(0); }       // 1-indexed
  add(i: number, delta: number) { for (; i < this.t.length; i += i & -i) this.t[i] += delta; }
  prefix(i: number) { let s = 0; for (; i > 0; i -= i & -i) s += this.t[i]; return s; }
  range(l: number, r: number) { return this.prefix(r) - this.prefix(l - 1); }  // inclusive, 1-based
}

class SegmentTreeMin {
  private t: number[];
  constructor(private n: number, a: number[]) {
    this.t = new Array(2 * n);
    for (let i = 0; i < n; i++) this.t[n + i] = a[i];                // leaves at n..2n−1
    for (let i = n - 1; i > 0; i--) this.t[i] = Math.min(this.t[2 * i], this.t[2 * i + 1]);
  }
  set(i: number, v: number) {
    for (this.t[i += this.n] = v; i > 1; i >>= 1) this.t[i >> 1] = Math.min(this.t[i], this.t[i ^ 1]);
  }
  query(l: number, r: number) {                                       // min over [l, r)
    let res = Infinity;
    for (l += this.n, r += this.n; l < r; l >>= 1, r >>= 1) {
      if (l & 1) res = Math.min(res, this.t[l++]);
      if (r & 1) res = Math.min(res, this.t[--r]);
    }
    return res;
  }
}
```

## When to use / when not to

**Recognition signals**
- Interleaved point updates and range queries ("Range Sum Query - Mutable").
- Counting inversions / "count of smaller numbers after self": iterate from the right, query a Fenwick tree over **ranks** (coordinate-compressed values), then add.
- Range min/max with updates; range add + range sum (lazy segment tree).

**When not to**
- Static array → prefix sums (sum) or a sparse table (min/max, O(1) query).
- Only the global min/max changes → a heap.
- Offline queries with a different structure might fit Mo's algorithm or sorting by endpoint.

## Trade-offs

| Structure | Update | Query | Range update | Aggregates | Code size |
| --- | --- | --- | --- | --- | --- |
| Prefix sums | O(n) | O(1) | O(n) | invertible (sum) | tiny |
| Fenwick | O(log n) | O(log n) prefix | with two trees | invertible (sum, xor) | ~10 lines |
| Segment tree | O(log n) | O(log n) | O(log n) lazy | any associative | 30–60 lines |
| Sparse table | rebuild | O(1) | — | idempotent (min, max, gcd) | small |

## Senior nuance

- **Fenwick needs invertibility** for range queries (`prefix(r) − prefix(l−1)`), so min/max ranges need a segment tree.
- **Coordinate compression** maps large or sparse values to 1..k before using them as indices — standard for inversion counting.
- **Iterative bottom-up segment trees** (as above) are compact and fast; recursive ones are easier to extend with lazy propagation.
- In production, the same idea appears as aggregated B-tree nodes or materialised rollups; interviews test the mechanism, not the library.

## Interview questions

<QA q="Count of Smaller Numbers After Self in O(n log n)." level="senior">
Coordinate-compress values to ranks 1..k. Iterate from right to left: the answer for nums[i] is fenwick.prefix(rank[i] − 1) (how many smaller values already seen to the right); then fenwick.add(rank[i], 1). Merge sort with index tracking is an alternative.
</QA>

<QA q="Why is a Fenwick update O(log n)?" level="mid">
Each step adds lowbit(i) to i, which moves the lowest set bit at least one position left. After at most log₂ n steps i exceeds n. The same bit argument bounds the query: every step clears one set bit.
</QA>

<QA q="How do you support 'add v to every element in [l, r]' and 'sum over [l, r]'?" level="senior">
Segment tree with lazy propagation: store a pending add at a node that is fully covered and push it to children only when a later operation needs to go deeper. Alternatively two Fenwick trees (one for the coefficient of i, one for constants) using the difference-array identity.
</QA>
