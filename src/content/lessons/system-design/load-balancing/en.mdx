## TL;DR

A <Term id="load-balancer" /> spreads requests across a pool of servers, removes unhealthy ones via **health checks**, and makes the pool look like one endpoint. **L4** balancers route TCP/UDP connections by address and port (fast, protocol-agnostic); **L7** balancers understand HTTP (route by path/host/header, terminate TLS, retry, rate-limit). The algorithm matters when requests are uneven: **round-robin** ignores load; **least-connections** adapts to it.

## Mechanism

Run the same uneven workload (long and short requests alternating) through both policies. Round-robin assigns by turn and piles the long requests onto the same server; least-connections sends each request to the server with the fewest in-flight requests.

**Algorithms**:
- **Round-robin / weighted round-robin** — simple, good when requests and servers are uniform (weights for bigger machines).
- **Least connections / least outstanding requests** — adapts to slow requests and heterogeneous servers.
- **Power of two choices** — pick two random servers, send to the less loaded: near-least-connections quality with no global state, ideal for many LB instances.
- **Consistent hashing** (by user/session/key) — keeps a client on the same backend (cache locality, sticky sessions) and minimises reshuffling when servers change.

**Health checks**: active (LB probes `/healthz` periodically) and passive (count errors/timeouts on real traffic and eject outliers). Use separate **liveness** and **readiness** semantics so a starting or draining server receives no traffic.

**Avoiding a single point of failure**: run LBs in redundant pairs or as a managed, horizontally scaled service; use DNS or anycast across regions; keep backends stateless so any server can handle any request.

## Code

```ts
// Power of two choices — no shared state needed between LB instances
function pick(servers: { id: string; inFlight: number; healthy: boolean }[]) {
  const live = servers.filter((s) => s.healthy);
  const a = live[Math.floor(Math.random() * live.length)];
  const b = live[Math.floor(Math.random() * live.length)];
  return a.inFlight <= b.inFlight ? a : b;
}

// Retries at the LB/client must be bounded and only for safe/idempotent requests
async function withRetry<T>(fn: () => Promise<T>, attempts = 3): Promise<T> {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i === attempts - 1) throw e;
      await new Promise((r) => setTimeout(r, 2 ** i * 100 * (0.5 + Math.random())));  // backoff + jitter
    }
  }
}
```

## When to use / when not to

**L4** for raw TCP services (databases, MQTT, game servers), extreme throughput, or when you don't want TLS terminated at the balancer. **L7** for HTTP APIs: path-based routing to services, canary releases by header/percentage, auth offload, compression, observability per route.

**Sticky sessions** only when you can't externalise session state — they unbalance load and lose sessions when a server dies; prefer storing sessions in Redis/DB or in signed tokens.

## Trade-offs

| Algorithm | Needs state | Handles uneven requests | Cache affinity |
| --- | --- | --- | --- |
| Round-robin | counter | no | no |
| Least connections | live counts per backend | yes | no |
| Power of two choices | local counts | mostly | no |
| Consistent hashing | ring | no (hot keys!) | yes |

## Senior nuance

- **Retry storms**: if every layer retries 3×, one failing backend can see 27× traffic. Retry at one layer, with budgets (e.g. at most 10% extra requests) and jitter.
- **Slow start**: a newly added server with an empty cache should receive traffic gradually.
- **Connection draining**: on deploys, stop sending new requests to an instance and let existing ones finish (ties to graceful shutdown).
- **Global load balancing** routes users to the nearest healthy region; failover must account for capacity — the surviving region needs headroom for the failed one's traffic.

## Interview questions

<QA q="L4 vs L7 load balancing?" level="mid">
L4 works on transport-level information (IP, port) and forwards connections without understanding the protocol: very fast, works for any TCP/UDP service, but can't route by URL or inspect headers. L7 parses application protocols like HTTP: it can terminate TLS, route by host/path/header, rewrite, retry, rate-limit and collect per-route metrics, at the cost of more CPU and complexity.
</QA>

<QA q="Why might round-robin overload one server?" level="mid">
It distributes requests by count, not by cost. If request durations vary (or servers differ in capacity), a server can accumulate many long-running requests while others are idle. Least-connections, least-outstanding-requests or power-of-two-choices route based on current load.
</QA>

<QA q="How do you avoid the load balancer being a single point of failure?" level="senior">
Run it as a redundant pair with failover (VRRP/floating IP) or as a horizontally scaled managed service; put multiple LB IPs behind DNS or anycast; spread across availability zones; keep backends stateless; and test failover regularly. At global scale, use DNS/anycast-based global load balancing with health-aware region failover.
</QA>
