## TL;DR

<Term id="load-balancer" /> request'larni serverlar pool'i boʻylab taqsimlaydi, **health check**'lar orqali nosozlarini olib tashlaydi va pool'ni bitta endpoint'dek koʻrsatadi. **L4** balancer'lar TCP/UDP ulanishlarini manzil va port boʻyicha yoʻnaltiradi (tez, protokoldan mustaqil); **L7** balancer'lar HTTP'ni tushunadi (path/host/header boʻyicha yoʻnaltirish, TLS'ni tugatish, retry, rate-limit). Request'lar notekis boʻlganda algoritm muhim: **round-robin** yuklamani e'tiborsiz qoldiradi; **least-connections** unga moslashadi.

## Mexanizm

Bir xil notekis yuklamani (uzun va qisqa request'lar navbatma-navbat) ikkala siyosat orqali ishga tushiring. Round-robin navbat boʻyicha tayinlaydi va uzun request'larni bitta serverga yigʻadi; least-connections har bir request'ni jarayondagi request'lari eng kam serverga yuboradi.

**Algoritmlar**:
- **Round-robin / weighted round-robin** — sodda, request'lar va serverlar bir xil boʻlganda yaxshi (kattaroq mashinalar uchun vaznlar).
- **Least connections / least outstanding requests** — sekin request'lar va har xil serverlarga moslashadi.
- **Power of two choices** — ikkita tasodifiy server tanlab, kamroq yuklanganiga yuborish: global state'siz least-connections'ga yaqin sifat, koʻp LB nusxalari uchun ideal.
- **Consistent hashing** (foydalanuvchi/sessiya/key boʻyicha) — client'ni bir xil backend'da saqlaydi (cache locality, sticky session'lar) va serverlar oʻzgarganda qayta taqsimlashni minimallashtiradi.

**Health check'lar**: faol (LB `/healthz`ni davriy tekshiradi) va passiv (haqiqiy trafikdagi xato/timeout'larni sanab, chetga chiqqanlarni chiqaradi). Ishga tushayotgan yoki trafikdan chiqarilayotgan server trafik olmasligi uchun alohida **liveness** va **readiness** semantikasidan foydalaning.

**Yagona nosozlik nuqtasidan qochish**: LB'larni zaxira juftlik sifatida yoki boshqariladigan, gorizontal masshtablanadigan servis sifatida ishga tushiring; regionlar boʻylab DNS yoki anycast ishlating; istalgan server istalgan request'ni hal qila olishi uchun backend'larni stateless saqlang.

## Kod

```ts
// Power of two choices — LB nusxalari orasida umumiy state kerak emas
function pick(servers: { id: string; inFlight: number; healthy: boolean }[]) {
  const live = servers.filter((s) => s.healthy);
  const a = live[Math.floor(Math.random() * live.length)];
  const b = live[Math.floor(Math.random() * live.length)];
  return a.inFlight <= b.inFlight ? a : b;
}

// LB/client'dagi retry'lar cheklangan va faqat xavfsiz/idempotent request'lar uchun boʻlishi shart
async function withRetry<T>(fn: () => Promise<T>, attempts = 3): Promise<T> {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (i === attempts - 1) throw e;
      await new Promise((r) => setTimeout(r, 2 ** i * 100 * (0.5 + Math.random())));  // backoff + jitter
    }
  }
}
```

## Qachon ishlatiladi / ishlatilmaydi

**L4** xom TCP servislar (ma'lumotlar bazalari, MQTT, oʻyin serverlari), ekstremal throughput yoki TLS balancer'da tugatilishini xohlamaganingizda. **L7** HTTP API'lar uchun: servislarga path boʻyicha yoʻnaltirish, header/foiz boʻyicha canary relizlar, auth'ni yuklab olish, siqish, har route boʻyicha kuzatuvchanlik.

**Sticky session'lar** faqat sessiya state'ini tashqariga chiqara olmaganingizda — ular yuklamani notekis qiladi va server oʻlganda sessiyalarni yoʻqotadi; sessiyalarni Redis/DB'da yoki imzolangan token'larda saqlashni afzal koʻring.

## Trade-off'lar

| Algoritm | State kerakmi | Notekis request'larni hal qiladimi | Cache bogʻliqligi |
| --- | --- | --- | --- |
| Round-robin | hisoblagich | yoʻq | yoʻq |
| Least connections | har backend uchun jonli sonlar | ha | yoʻq |
| Power of two choices | lokal sonlar | asosan | yoʻq |
| Consistent hashing | halqa | yoʻq (hot key'lar!) | ha |

## Senior nuance

- **Retry boʻronlari**: har bir qatlam 3× retry qilsa, bitta nosoz backend 27× trafik koʻrishi mumkin. Bitta qatlamda, byudjetlar bilan (masalan, koʻpi bilan 10% qoʻshimcha request) va jitter bilan retry qiling.
- **Sekin start**: cache'i boʻsh yangi qoʻshilgan server trafikni asta-sekin olishi kerak.
- **Ulanishlarni chiqarish (draining)**: deploy'larda nusxaga yangi request'lar yuborishni toʻxtating va mavjudlari tugashiga yoʻl qoʻying (graceful shutdown bilan bogʻliq).
- **Global load balancing** foydalanuvchilarni eng yaqin sogʻlom regionga yoʻnaltiradi; failover sigʻimni hisobga olishi shart — omon qolgan region nosozining trafigi uchun zaxiraga ega boʻlishi kerak.

## Interview savollari

<QA q="L4 va L7 load balancing?" level="mid">
L4 transport darajasidagi ma'lumot (IP, port) bilan ishlaydi va protokolni tushunmasdan ulanishlarni uzatadi: juda tez, istalgan TCP/UDP servis uchun ishlaydi, lekin URL boʻyicha yoʻnaltira olmaydi yoki header'larni tekshira olmaydi. L7 HTTP kabi ilova protokollarini parse qiladi: TLS'ni tugatishi, host/path/header boʻyicha yoʻnaltirishi, qayta yozishi, retry, rate-limit qilishi va har route boʻyicha metrikalar yigʻishi mumkin — koʻproq CPU va murakkablik evaziga.
</QA>

<QA q="Nega round-robin bitta serverni ortiqcha yuklashi mumkin?" level="mid">
U request'larni narx boʻyicha emas, soni boʻyicha taqsimlaydi. Request davomiyliklari har xil boʻlsa (yoki serverlar sigʻimi farq qilsa), bir server koʻp uzoq ishlaydigan request'larni yigʻishi, boshqalari esa boʻsh turishi mumkin. Least-connections, least-outstanding-requests yoki power-of-two-choices joriy yuklama asosida yoʻnaltiradi.
</QA>

<QA q="Load balancer yagona nosozlik nuqtasi boʻlib qolishidan qanday qochasiz?" level="senior">
Uni failover'li (VRRP/floating IP) zaxira juftlik sifatida yoki gorizontal masshtablanadigan boshqariladigan servis sifatida ishga tushiring; bir nechta LB IP'ni DNS yoki anycast ortiga qoʻying; availability zone'lar boʻylab tarqating; backend'larni stateless saqlang; va failover'ni muntazam test qiling. Global masshtabda salomatlikni hisobga oladigan region failover'li DNS/anycast asosidagi global load balancing'dan foydalaning.
</QA>
