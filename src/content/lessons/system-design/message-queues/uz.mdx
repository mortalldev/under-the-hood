## TL;DR

Asinxron xabar almashish producer'larni consumer'lardan **vaqt** (consumer ishlamay turishi mumkin), **tezlik** (portlashlarni buffer'lash) va **bilim** (producer kim tinglayotganini bilmaydi) boʻyicha ajratadi. Ikki oila: **queue**'lar (har bir xabarni bitta consumer qayta ishlaydi, keyin olib tashlanadi — ish taqsimlash) va **log/stream**'lar (xabarlar tartibda saqlanadi; koʻp consumer group'lar oʻz offset'larida oʻqiydi — event tarqatish va qayta oʻynash). Yetkazish deyarli doim **at-least-once**, shuning uchun consumer'lar **idempotent** boʻlishi shart; tartib faqat **partition ichida** kafolatlanadi.

## Mexanizm

**Yetkazish kafolatlari**:
- **At-most-once**: qayta ishlashdan oldin ack — qulashlar xabarlarni yoʻqotadi.
- **At-least-once**: qayta ishlash, keyin ack — qulashlar qayta yetkazishga (dublikatlarga) olib keladi. Standart tanlov.
- **Exactly-once processing**: at-least-once yetkazish + <Term id="idempotency" /> (xabar ID boʻyicha dedupe, upsert'lar, shartli yozishlar) yoki bitta tizim ichidagi tranzaksion qayta ishlash orqali oxiridan-oxirigacha erishiladi.

**Tartib**: log tartibni **partition** boʻyicha saqlaydi. Tartibli qolishi kerak boʻlgan xabarlar (bitta buyurtmaning barcha event'lari) uni boʻlishishi uchun partition key'ni tanlang. Koʻproq partition = koʻproq parallelizm, lekin global tartib yoʻq.

**Backpressure va retry'lar**: queue portlashlarni yutadi, lekin consumer lag kuzatilishi shart. Retry'lar eksponensial backoff ishlatadi; doim muvaffaqiyatsiz boʻladigan xabarlar partition'ni abadiy bloklash oʻrniga **dead-letter queue**'ga boradi.

**Dual-write muammosi**: DB'ga yozib, keyin broker'ga e'lon qilish oraliqda muvaffaqiyatsiz boʻlib, ularni nomuvofiq qoldirishi mumkin. <Term id="outbox-pattern" /> event'ni state oʻzgarishi bilan **bitta tranzaksiyada** outbox jadvaliga yozadi; relay (polling yoki change-data-capture) uni e'lon qiladi.

## Kod

```ts
// Tranzaksion outbox (producer)
await db.transaction(async (tx) => {
  const order = await tx.orders.insert({ userId, items, status: "placed" });
  await tx.outbox.insert({ topic: "order-events", key: order.id, payload: { type: "OrderPlaced", orderId: order.id } });
});
// Alohida relay e'lon qilinmagan outbox qatorlarini oʻqiydi, e'lon qiladi, yuborilgan deb belgilaydi (at-least-once).

// Idempotent consumer
async function onOrderPlaced(msg: { id: string; payload: { orderId: string } }) {
  const firstTime = await db.processed.insertIfAbsent(msg.id);   // xabar id'sida unique cheklov
  if (!firstTime) return;                                         // takroriy yetkazish → hech narsa qilmaslik
  await sendConfirmationEmail(msg.payload.orderId);
}
```

## Qachon ishlatiladi / ishlatilmaydi

**Xabar almashishdan foydalaning**: keyinroq bajarilishi mumkin boʻlgan ish (email'lar, thumbnail'lar, hisobotlar), trafik choʻqqilarini tekislash, domen event'larini koʻp servislarga tarqatish, mavjudligi har xil tizimlarni integratsiya qilish, event sourcing/CDC pipeline'lari uchun.

**Foydalanmang**: chaqiruvchiga natija hozir kerak boʻlganda (sinxron request/response soddaroq), DB jadvali + cron job yetadigan kichik tizimlar uchun yoki tuzatish mumkin boʻlgan sekin bogʻliqlikni yashirish usuli sifatida.

## Trade-off'lar

| | Queue (masalan RabbitMQ, SQS) | Log/stream (masalan Kafka, Kinesis) |
| --- | --- | --- |
| Iste'mol | raqobatlashuvchi consumer'lar, ack'dan keyin xabar olib tashlanadi | offset'li consumer group'lar, xabarlar saqlanadi |
| Qayta oʻynash | yoʻq (iste'mol qilingach) | ha, saqlash muddati ichida |
| Tartib | queue boʻyicha (parallel consumer'lar bilan koʻpincha boʻshashtiriladi) | partition boʻyicha |
| Routing | boy (exchange'lar, topic'lar, ustuvorliklar, kechikishlar) | topic/partition boʻyicha |
| Odatiy qoʻllanish | task taqsimlash | event streaming, CDC, analitika |

## Senior nuance

- **Zaharli xabarlar** tartibli consumer'larda partition'ni bloklaydi — retry'larni cheklang va ularni keyinroq qayta oʻynash uchun yetarli kontekst bilan DLQ'ga koʻchiring.
- **Consumer lag** — asosiy SLO metrikasi; faqat xatolarga emas, lag oʻsishiga alert qoʻying.
- **Schema evolyutsiyasi**: event'lar — ommaviy shartnoma; ularni versiyalang, field'larni mos tarzda qoʻshing, qat'iy tiplangan pipeline'lar uchun schema registry ishlating.
- **Saga'lar** koʻp servisli ish oqimlarini taqsimlangan tranzaksiyalar oʻrniga kompensatsiya amallari bilan muvofiqlashtiradi (masalan, zaxirani band qilish → yechib olish → muvaffaqiyatsizlikda zaxirani boʻshatish).
- Consumer group'larning **rebalancing**'i iste'molni qisqa toʻxtatadi; har xabarga qayta ishlashni qisqa saqlang va offset'larni side effect'lardan keyin commit qiling.

## Interview savollari

<QA q="Message broker bilan exactly-once semantikasini qanday olasiz?" level="senior">
Tarmoqlar faqat at-most-once yoki at-least-once yetkazishga imkon beradi. At-least-once'ni tanlang (qayta ishlashdan keyin ack/commit) va ta'sirni idempotent qiling: side effect bilan tranzaksion saqlanadigan noyob xabar ID boʻyicha dedupe qiling, upsert/shartli yozishlardan foydalaning yoki ikkalasi bitta tizimda yashasa, qayta ishlash va offset commit'larini bitta tranzaksiyada saqlang. Natija — takroriy yetkazishlarga qaramay exactly-once ta'sir.
</QA>

<QA q="Outbox pattern nima va nega u kerak?" level="mid">
Servislar koʻpincha ma'lumotlar bazasini yangilashi va event e'lon qilishi kerak. Ikkalasini alohida qilish biri muvaffaqiyatsiz boʻlsa nomuvofiqlik xavfini tugʻdiradi. Outbox pattern event'ni state oʻzgarishi bilan bitta ma'lumotlar bazasi tranzaksiyasida outbox jadvaliga yozadi; relay keyinroq outbox yozuvlarini broker'ga e'lon qiladi (at-least-once), shuning uchun event faqat oʻzgarish commit boʻlgandagina e'lon qilinadi.
</QA>

<QA q="Consumer'larni masshtablagan holda har mijoz boʻyicha tartibni qanday saqlaysiz?" level="mid">
Topic'ni mijoz ID boʻyicha partition qiling, shunda mijozning barcha event'lari bitta partition'ga tushadi, uni esa guruhdagi bir vaqtda bitta consumer iste'mol qiladi. Partition'larni oshirib masshtablang; tartib global emas, partition boʻyicha (mijoz boʻyicha) kafolatlanadi.
</QA>
